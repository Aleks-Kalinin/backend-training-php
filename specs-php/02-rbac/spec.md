# Feature: Role-Based Access Control (RBAC)

## 1. Overview

* **Purpose:** Provide database-driven, dynamic authorization without application restarts.
* **Target Roles:** Administrators manage policy; users receive one or more roles.
* **Authentication:** Laravel session middleware; authorization is separate.
* **Dependencies:** PostgreSQL, Laravel Gates/Policies, shared Redis cache for multi-instance invalidation.

## 2. Core Entities

* **Role:** `id`, unique `name`, optional `description`.
* **Permission:** `id`, unique resource `name`, allowed `actions[]`, optional field visibility/write policy.
* **Grant:** `id`, `roleId`, `permissionId`, optional `actions[]`.
* **UserRole:** User-to-role mapping.
* If a grant's `actions` is omitted or empty, it allows all actions defined for the granted permission.
* Field-level policies default to deny: fields not explicitly allowed are omitted from administrative reads and cannot be modified.

## 3. Technical Contract

### 3.1 Access Check

The authorization service receives the authenticated user, permission key, and requested action. It loads grants for assigned roles and allows access only if a matching grant exists and its action list is empty or includes the requested action. Otherwise, deny with `403 Forbidden`.

Use Laravel policies/Gates or permission middleware as the integration point; do not place RBAC policy logic inside session authentication.

### 3.2 Administrative Management API

All routes require an authenticated session and the appropriate RBAC administration permission.

* `GET /admin/rbac/roles`
* `POST /admin/rbac/roles`
* `PUT /admin/rbac/roles/{roleId}`
* `DELETE /admin/rbac/roles/{roleId}` — reject deletion while grants or user assignments remain.
* `GET /admin/rbac/permissions`
* `POST /admin/rbac/permissions`
* `PUT /admin/rbac/permissions/{permissionId}`
* `DELETE /admin/rbac/permissions/{permissionId}` — reject deletion while grants remain.
* `GET /admin/rbac/grants`
* `POST /admin/rbac/grants`
* `PUT /admin/rbac/grants/{grantId}`
* `DELETE /admin/rbac/grants/{grantId}`

Payloads:

* Role: `{ name: string, description?: string }`
* Permission: `{ name: string, actions: string[], readableFields?: string[], writableFields?: string[] }`
* Grant: `{ roleId: string, permissionId: string, actions?: string[] }`

IDs are generated by the server; clients MUST NOT choose or change entity IDs.

## 4. Persistence, Cache, and Dynamic Updates

* Enforce unique role names, permission names, and role/permission grant pairs in PostgreSQL.
* Perform related mutations transactionally.
* Invalidate shared cached authorization configuration after every role, permission, grant, or user-role mutation.
* Cache invalidation MUST be visible across all application instances; do not rely on process-local memory as the source of truth.
* A cache miss/reload must read committed database state. Authorization MUST fail closed if policy state cannot be loaded.
* Redis is the recommended shared cache; PostgreSQL remains the source of truth.

## 5. Error Handling

* `400 Bad Request`: Invalid action arrays, malformed payload, or invalid field policy.
* `403 Forbidden`: Missing required permission or unauthorized management operation.
* `404 Not Found`: Target entity does not exist.
* `409 Conflict`: Duplicate names/mappings or deletion blocked by bindings.

## 6. Audit and Security

Log actor ID, operation, target entity ID/type, status, and cache invalidation/reload outcome. Do not log sensitive profile field values. Require administrator authorization for management endpoints and validate all fields against allowlists.
